# Fidelity-first Quran recitation recognition — research & design report

Status: **research only.** Nothing here is implemented. Scoring, learning state, review scheduling and production STT are unchanged.
Date: 2026-10-06. Companion docs: [STT-QURAN.md](STT-QURAN.md), [LEARNING-MODEL.md](LEARNING-MODEL.md).

## 1. Requirement (non-negotiable)

> The acoustic evidence is authoritative. The known Quran text may be used for alignment *after* recognition, but must never silently repair what the learner said.

Product consequence: a recognizer that "corrects" a learner invalidates the memorization feature, because the feature's output *is* the learner's mistakes.

## 2. Preserved benchmark results (real recordings, dev benchmark `/dev/stt-benchmark`)

Deliberate-error case. Spoken (ground truth, typed by the tester): `اهدنا الطريق المستقيم`. No prompt, same audio blob for every model.

| model | returned | verdict vs. what was SPOKEN |
|---|---|---|
| whisper-1 | `الطريق` preserved | literal on this case |
| gpt-4o-transcribe | `الصراط` | **silent correction toward the Quran** |
| gpt-4o-mini-transcribe | `الصراط` | silent correction |
| gpt-4o-mini-transcribe-2025-12-15 | `الصراط` | silent correction |
| gpt-transcribe | `الصراط` | silent correction |

Earlier real recordings: whisper-1 sometimes returned unrelated phrases (e.g. `اشتركوا في القناة` — a known Whisper-family hallucination on silence/noise, likely a training-data artefact).

Reading: the two failure modes are different and both disqualify a general-purpose model as the *sole* authority.
- GPT-4o family: a strong language-model prior that rewrites rare/wrong words into the most probable (here: Quranic) word. Fidelity failure.
- whisper-1: more literal, but unconstrained generation → hallucination on non-speech. Reliability failure.
- Neither family is selected as production primary. No heuristics are added.

Important consequence for confidence: **an autoregressive decoder's token probability is not acoustic evidence.** When a model "corrects" toward a likely word, the corrected word will usually carry *high* probability (the language model is sure of it). So the per-token log-probabilities we already collect from gpt-4o cannot be used to detect its own corrections. (Hypothesis consistent with the benchmark; it can be checked from the saved JSON: look at the probability gpt-4o attached to `الصراط` on the `الطريق` recording.)

## 3. Why the failure is architectural

| property | encoder-decoder / LLM-style ASR (Whisper, GPT-4o) | CTC acoustic model (wav2vec2 / XLS-R / MMS heads) |
|---|---|---|
| output generated by | autoregressive decoder with a language model | per-frame independent label posteriors, collapsed |
| can "complete" an unfinished ayah | yes | no (nothing to emit without audio) |
| can "repair" a wrong word to a likelier one | yes — this is the benchmark failure | only to the extent the *acoustics* support it |
| hallucinates on silence | yes | emits blanks |
| confidence | token prob. dominated by LM prior | frame/char posteriors, closer to acoustic evidence |
| word timings | whisper: approximate; gpt-4o: none | native (frame-level alignment) |

The principle: the component that decides *what was said* must not be able to see, or be biased by, the expected text, and must not contain a strong text prior.

## 4. Candidate approaches

Cost/latency figures are order-of-magnitude estimates, not measurements; none were benchmarked here. Items marked ⚠ could not be fully verified in this research (gated pages, claims by authors).

### A. OpenAI hosted STT (whisper-1, gpt-4o-*) — *measured*
- Quran accuracy: see §2. General Arabic LM prior; no Quran-specific training signal.
- Confidence: whisper-1 segment stats only; gpt-4o token probs (LM-biased, see §2). No phoneme level.
- Cost/latency: per-minute API pricing; ~1–3 s per short clip (measured in the benchmark UI).
- Difficulty: done. Privacy: audio leaves to a third party (no retention configured on our side).
- Verdict: not authoritative. Possible only as a *secondary cross-check*, never as the source of truth.

### B. Open Whisper fine-tuned on Quran (e.g. `tarteel-ai/whisper-*-ar-quran`, Whisper-large-v3 speech-to-phoneme from Iqra'Eval teams)
- Trained mostly on professional reciters (EveryAyah) with diacritized Quran text → strong *Quran-text prior* → **likely to correct amateur/erroneous recitation toward the verse** (same failure as §2, concentrated on exactly the text we care about). A fine-tuned Whisper tiny reports ~7% WER on its in-domain eval (model card) — in-domain on clean reciters, not on learners making errors.
- The Iqra'Eval 2025 phoneme-level system based on Whisper-large-v3 reports F1 ≈ 0.32 for error detection (shared-task paper) — error detection is hard even for fine-tuned systems.
- Confidence: same decoder limitation as A. Self-hostable (privacy ✔), GPU recommended for base/large. Difficulty: medium.
- Verdict: good for *verse identification / "which ayah is this"* (use-case where the prior helps), wrong as the fidelity authority.

### C. CTC acoustic models fine-tuned for Quranic Arabic (wav2vec2 / XLS-R / MMS) — **character or phoneme output**
- Examples found on Hugging Face: `rabah2026/wav2vec2-large-xlsr-53-arabic-quran-v_final` (XLS-R 53 Arabic, Quran-Ayah-Corpus), and `quran-dev/wav2vec2-ctc-quran-phoneme-*` (71-symbol phoneme vocabulary, tajweed-aware). ⚠ The `quran-dev` page returned HTTP 401 to me, so licence, training data and metrics are **unverified**; treat as leads, not choices.
- Fidelity: ✔ best structural fit — no autoregressive text prior, greedy/beam decoding with **no language model** keeps it literal. A small amount of LM-free character prior is learned in the encoder, which is the residual risk to measure.
- Quran accuracy: unknown for amateur speakers (training data = professional reciters). Domain shift to learners (accent, noise, phone mic) is the main risk → needs our own evaluation set (§6) and likely fine-tuning on learner-style audio.
- Confidence: ✔ real per-frame posteriors → per-character/phoneme and per-word confidence (min/mean over the aligned span, or GOP).
- Cost: self-hosted, ~300M params (large) → CPU int8/ONNX roughly 1–4 s for a 5–15 s clip; GPU well under 1 s; small GPU instance or CPU workers. No per-minute fee.
- Privacy: ✔ audio never leaves our infrastructure; on-device (ONNX/WebGPU) is feasible later for a quantized model (~100–300 MB).
- Difficulty: medium-high (Python inference service, audio decoding/resampling, VAD, versioned model artefacts).

### D. Reference-aware mispronunciation detection (MDD) research systems (Iqra'Eval 2025/Iqra'Eval2)
- Task: given audio + reference text, find phoneme-level errors. Systems: ShallowTransformer on wav2vec2 features, multi-stage fine-tuned wav2vec2, Whisper-v3 speech-to-phoneme.
- Key finding for us: the literature itself identifies *canonical-prior bias* as the central problem — "explicit canonical priors bias predictions toward intended targets" — and the best recent line (CROTTC-IF, reported ~71.7 % F1 on Iqra'Eval2) is explicitly **prompt-free**, i.e. decouples acoustics from the reference. This independently supports our requirement. ⚠ Numbers are the authors' claims on a shared-task set (not our users).
- Verdict: use as design guidance and as an offline reference for evaluation, not a drop-in product. Phoneme-level/tajweed claims are out of scope for the MVP anyway.

### E. Forced alignment (reference-aware, *after* recognition)
- CTC forced alignment (e.g. `torchaudio.functional.forced_align`, MMS aligner, NeMo Forced Aligner): aligns a *known token sequence* to the audio posteriors and returns per-token timing and scores. Montreal Forced Aligner (Kaldi) needs an Arabic acoustic model + pronunciation lexicon (heavier).
- **Danger:** forced alignment *assumes* the text was spoken and will always produce an alignment. Used alone it is exactly the silent-repair failure. It is only safe as the *second* of two independent passes (§5), where its score is compared against a reference-blind recognition.
- Cost: negligible (Viterbi over posteriors). Confidence: native.

### F. Commercial / other
- Tarteel (closed): reports >96 % error detection with a NeMo-based model; closed, no public API I could confirm. ⚠ Vendor claim; a partnership/licensing conversation would be the route, not an integration we can assume.
- Azure/Google Arabic STT: general-purpose recognizers with the same text-prior behaviour as A; custom-phrase boosting would *increase* correction toward expected text. Not recommended; not benchmarked.
- Browser Web Speech API: no control over model, behaviour varies by browser/OS, audio goes to the vendor. Already a weak option; keep only as fallback with the lowest trust.

## 5. Recommended architecture for مُذَكِّر

### Principle: two independent passes, reference never feeds the recognizer

```
audio ──► VAD / quality gate ──► Pass 1: REFERENCE-BLIND acoustic recognition (CTC, no LM)
                                      │  frame posteriors + literal char/word hypothesis
                                      ▼
canonical ayah text ──► Pass 2: forced alignment / scoring of the canonical text against the SAME posteriors
                                      ▼
                        Comparison layer (read-only): per word → evidence → verdict
```

**Pass 1 – "what was said"** (authoritative). A CTC character (later phoneme) model, decoded greedily **without** a language model and **without** being given the verse. Its literal output is stored as *the transcript* — unmodified.

**Pass 2 – "how well does the expected word fit the audio"**. CTC forced alignment of the canonical words over the same posteriors gives, per word: time span, and a goodness score = log P(canonical chars | audio) relative to the best free path (a GOP-style ratio). This is *scoring evidence*, never a rewrite of Pass 1.

**Comparison layer** (pure function; output states, per word):
| Pass 1 free decode | Pass 2 fit to canonical | Verdict |
|---|---|---|
| equals canonical | high | **correct** |
| different word, high posterior | canonical fits poorly | **learner-different** (substitution) — the only state that may count against the learner |
| blank / silence over the canonical span | poor | **omission** (if the surrounding words are confidently aligned) |
| extra word spans with no canonical counterpart | n/a | **addition**; same canonical word spanning twice → **repetition** |
| free decode and canonical both low/competing, noise, low SNR | ambiguous | **uncertain** («لم نتأكد — أعد هذا الجزء») |
| nothing speech-like (VAD / blank dominated) | n/a | **no speech** — never a transcript, never a score |

"Recognizer uncertain" vs "learner wrong" then rests on *measured acoustic posteriors*, not on spelling-similarity heuristics (the confusion table in `confusion.ts` is retired by this design; it is not extended).

**Safeguards that fall out of the structure**
- Pass 1 cannot complete an unfinished ayah or fill an omitted word: there is no audio to emit labels for.
- Silence/noise → blanks, not "اشتركوا في القناة". An energy/VAD gate runs before inference regardless.
- The canonical text is only an input to Pass 2 and to the verdict table.
- Every verdict carries its evidence (posterior, span) so it is auditable and debuggable (extends the existing `STT_TRACE` idea; still no audio stored).

### Role for the existing providers
- OpenAI models: **demoted to optional cross-checks** in shadow/diagnostic mode (e.g. flag when Pass 1 and whisper-1 disagree on a word). They never decide and never feed the score. Never send the canonical text or an ayah-specific prompt.
- Verse identification ("which ayah did the user start?"), if ever needed, may use a Whisper-Quran model *or* the reference-blind CTC output matched to the corpus — it identifies the passage, then the passage is aligned in Pass 2.

### Deployment shape
A small stateless Python inference service (own container, same `docker-compose`), behind the existing `SpeechToTextProvider` interface (`src/server/stt/provider.ts`) as a new provider returning `{ text, words[{text,start,end,confidence}], evidence }`. Audio held in memory only, as today. Model weights pinned and versioned; the version is recorded with each analysis.

## 6. How to decide — evaluation before any build

Build a **gold set** with the dev benchmark (it already collects spoken ground truth, audio kept only locally for the evaluation, with consent):
- ≥ 100 clips, several speakers/devices/noise levels, spanning: correct recitation, deliberate substitution, omission, addition, repetition, stop-halfway, silence, background noise, children/adult/male/female, different dialects.
- Metrics (not "matches the Quran"):
  1. **Fidelity**: literal-transcript rate on deliberate-error clips; **silent-correction rate** (must be ≈ 0).
  2. **Hallucination rate** on silence/noise clips (must be ≈ 0).
  3. Substitution/omission/addition/repetition **precision and recall**, per-word.
  4. **Uncertain-vs-wrong calibration**: of words marked learner-different, what fraction really differ (target high precision — a false accusation of a memorization error is the costliest error).
  5. Latency p50/p95 and cost per recitation.
- Candidates to run offline on that set: the XLS-R/phoneme CTC checkpoints (after licence check), a Quran-tuned Whisper, whisper-1 (control), gpt-4o (negative control). Selection = best fidelity/hallucination, then precision.
- Gate for adoption: silent-correction ≈ 0, hallucination ≈ 0, high precision on learner-different. If no candidate passes on learner audio, the next step is fine-tuning the CTC model on collected learner audio, not heuristics.

## 7. Risks and unknowns (stated plainly)
- No open Quran CTC model has been validated here on amateur recitation; all accuracy statements about them are expectations, not measurements.
- Pretraining on professional reciters will degrade on children, accents and phone microphones; fine-tuning data (with consent, privacy review) may be required.
- Tajweed-level judgments (madd, ghunnah, ikhfa) remain out of scope; word/character fidelity only.
- Different qira'at and valid waqf/wasl variants need a policy (accept-list per ayah) before verdicts are shown as "wrong".
- Collecting learner audio for evaluation/fine-tuning is a privacy-sensitive step: explicit opt-in, retention limits, and an update to `PRIVACY-DATA-INVENTORY.md` before any collection.

## 8. Phased plan (no work started)
0. Gold set + evaluation harness (extends the existing benchmark page; no production change).
1. Offline bake-off of candidates (§6).
2. Prototype Pass 1 + Pass 2 service; shadow mode alongside current STT, results logged, never shown.
3. Calibrate the verdict table on the gold set; define thresholds from data.
4. Integrate behind the provider interface; scoring consumes only {correct, learner-different, omission, addition, repetition, uncertain, no-speech}.
